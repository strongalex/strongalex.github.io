<h1>RBE 3000s</h1>

<p>My junior year robotics sequence ran across three courses, each attacking a different layer of the stack: the math that moves an arm, the autonomy that navigates a space, and the software architecture that holds a robot system together.</p>

<hr>

<h2>RBE 3001: Manipulation</h2>
<p><em>C-Term 2026 &middot; MATLAB &middot; OpenManipulator-X</em></p>

<p>This course centered on robotic arms: position and velocity kinematics, trajectory generation, and vision-based tracking. The term built up through a series of labs and culminated in an autonomous pick-and-place sorting system.</p>

<p>I derived the forward kinematics using standard Denavit-Hartenberg parameterization, assigning frames to each joint and building the transformation chain in MATLAB. To validate the derivation before touching hardware, I built an interactive 3D model of the arm in Desmos that computes each joint position from the DH parameters. Dragging the joint angles and watching the rendered pose surfaced sign errors and offset mistakes in seconds, which saved a lot of debugging time on the physical robot.</p>

<p>For inverse kinematics, I reduced the 3D problem to a planar 2-DOF one: the base joint rotates about the vertical axis, so the remaining joints always operate in a single vertical plane that rotates with it. Solving the base rotation first, then projecting the target into that plane, left a geometry problem the Law of Cosines handles directly. I added an end-effector angle constraint so the gripper orientation at the target could be controlled independently, which is what makes a grasp reliable once the arm arrives.</p>

<p>The final project integrated all of it with computer vision:</p>
<ul>
  <li>Intrinsic camera calibration to correct optical distortion, and extrinsic calibration to register the camera's image plane with the robot's base frame</li>
  <li>Color-based segmentation and centroid tracking to locate spheres in the workspace</li>
  <li>A geometric height-correction model, since a sphere's apparent centroid shifts with its position relative to the camera</li>
  <li>Velocity kinematics via the manipulator Jacobian to generate smooth trajectories and identify singular configurations</li>
</ul>
<p>The architecture deliberately decoupled the vision pipeline from the motion control logic, so either could be developed and debugged on its own.</p>

<h2>RBE 3002: Unified Robotics IV</h2>
<p><em>D-Term 2026 &middot; ROS 2 &middot; TurtleBot3</em></p>

<p>Here the robot had to explore and map an unknown maze on its own, then navigate it. My team wrote our own ROS 2 planner and controller around SLAM Toolbox, leaving the pre-made nav2 versions on the shelf.</p>

<img class="img-fluid rounded my-3" src="../img/classes/3002gazebo.png" alt="Gazebo simulation of the TurtleBot3 mapping the maze environment">

<p><strong>Mapping and cost representation.</strong> SLAM Toolbox consumes filtered LiDAR scans and wheel-encoder/IMU odometry to build a 2D occupancy grid while correcting for drift via scan matching. On the physical TurtleBot3 its scan matching degraded because of inconsistent point counts between scans, so we wrote a filter that republished cleaned readings to a separate topic. On top of the raw grid we built two layers: a hard obstacle inflation that marks any cell within the robot's radius plus clearance as occupied, and a separate risk gradient that falls off linearly with distance from obstacles. The gradient nudges the planner toward the middle of open space while still allowing tight passages when they are the only route.</p>

<p><strong>Frontier exploration.</strong> Finding where to go next is a three-phase search: a breadth-first pass to determine reachable space, a second pass to identify unknown cells at the boundary, and a flood fill to group those cells into distinct frontiers. Each frontier gets a centroid, and we scored candidates on distance, frontier size, and how far the robot would have to turn to face it. We ended up weighting purely on distance, since clearing nearby frontiers first beat chasing larger ones and doubling back later.</p>

<p><strong>Control flow.</strong> A finite state machine sequences the whole run through five states (idle, driving, waiting, navigating, returning), handling the startup calibration drive, the exploration loop, and the return home once no frontiers remain. Path planning throughout is A* over the inflated cost map, executed by a custom vector pursuit controller.</p>

<p><strong>Localization.</strong> The final phase was the kidnapping problem: staff place the robot somewhere arbitrary and it has to figure out where it is, then navigate to a goal. We implemented two approaches. AMCL uses a particle filter to estimate pose against a known map. SLAM Toolbox's lifelong mapping mode localizes well given a reasonable initial pose estimate, and keeps updating the map if the environment has changed.</p>

<h2>RBE 300x: Software Design for Robotics</h2>
<p><em>C-Term 2026 &middot; Python &middot; CoppeliaSim</em></p>

<p>The premise of this course is "build your own ROS." We implemented the architectural patterns that sit underneath a real middleware: publish-subscribe messaging, request-reply services, finite state machines, behavior trees, and the subsumption architecture. That meant dealing directly with the concurrency problems that come with them, including threads, callbacks, race conditions, and deadlocks.</p>

<p>The final lab was a warehouse delivery robot that pulled the whole term together into a layered architecture:</p>
<ul>
  <li>A <strong>Dispatcher</strong> node holding the record of pending deliveries, communicating over a request-reply pattern we implemented ourselves</li>
  <li>A <strong>behavior tree</strong> for high-level mission control, tracking the current goal, requesting the next delivery when idle or finished, and handling interrupts by priority</li>
  <li>A <strong>finite state machine</strong> for navigation, subscribing to the goal topic and driving the robot through the environment's intersections</li>
</ul>

<p>Nodes were launched from a YAML configuration file, so changing the system's composition meant editing data. The course also enforced real software practice throughout, including PEP8, meaningful Git history, issue tracking, and pull requests, which made it as much a software engineering course as a robotics one.</p>
